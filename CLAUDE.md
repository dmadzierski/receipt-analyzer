# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Receipt Analyzer digitizes receipts (PDF via Tesseract OCR, or JSON exports) into wallets of expenses. A main goal is collecting versioned, human-corrected receipt data to train an ML model, so the revision history is a core concept, not an afterthought.

Two apps live in this repo:
- `receipt-analyzer-service/`: Java 21 / Spring Boot 3.5 backend, multi-module Gradle (Kotlin DSL, version catalog in `gradle/libs.versions.toml`)
- `web-client/`: Angular 20 standalone app with Angular Material + Bootstrap, auth via `keycloak-angular`

## Commands

Backend (run from `receipt-analyzer-service/`):
```bash
./gradlew build                      # compile all modules and run all tests
./gradlew :monolith:bootJar          # build the runnable jar (what the Dockerfile does)
./gradlew :monolith:bootRun          # run locally (needs the env vars below)
./gradlew test                       # all tests (what Jenkins runs)
./gradlew :domain:test               # domain unit tests, no Spring or Docker
./gradlew :monolith:test              # integration tests, need Docker running (Testcontainers)
./gradlew :monolith:test --tests '*ReceiptFacadeIT'          # single test class
./gradlew :monolith:test --tests '*ApplicationModulesUT'     # Spring Modulith module rules, no Docker
```
Domain unit tests live in `domain/src/test` (JUnit 5 + AssertJ), in the same package as the class under test because domain classes are package-private. They cover the behaviour of domain objects (e.g. `ReceiptRevision`, `ReceiptItem`) without Spring or a database. Unit test classes end with `UT` (e.g. `ReceiptRevisionUT`), integration test classes with `IT`. The one unit test outside `domain` is `ApplicationModulesUT` in `monolith/src/test`, because it needs the application class; it starts no Spring context and no containers.

Integration tests live in `monolith/src/test` (the only module with the Spring Boot application class): `IntegrationTest` starts one `postgres:17`, one `mongo:8` and one `apache/kafka` container with Testcontainers for the whole run (`@ServiceConnection` wires them) and Flyway migrates Postgres from scratch, so Docker must be running. Each test runs in a rolled-back transaction, uploads go to `monolith/build/test-uploads`, and Keycloak is never contacted. Mongo is not transactional, so `IntegrationTest` empties the read model before each test, and `flush()` (flush + clear) also rebuilds the read model from Postgres (`ReadModelRebuild.projectDirectly()`): call it after writes or JDBC seeding, before any facade read or plain-SQL check. The test profile switches off the resubmission schedule, the Kafka listener and the start-up rebuild; `EventExternalizationIT` and `ReadModelPipelineIT` test the real path through Kafka, `ReadModelProjectionIT` replays outbox events one by one (`projectOutboxEvents()`) and checks they give the same read model as a rebuild. Receipt fixtures are in `monolith/src/test/resources/receipts`.

Frontend (run from `web-client/`):
```bash
npm start        # ng serve, app served at http://localhost:4200/home/
npm run build
npm test         # Karma/Jasmine
npx ng test --include='src/app/path/to/file.spec.ts'   # single spec
```

Local stack: `docker compose -f docker-compose.local.yml up` (from the repo root) starts PostgreSQL 17, MongoDB 8, Kafka (KRaft, one node; port 29092 for a backend run outside Docker), Keycloak (`start-dev --import-realm`, served under `/auth`), Nginx on port 80 and the backend (port 8090, JDWP debug port 5005). Variables come from the root `.env` (gitignored). MongoDB has its own root user (`MONGO_USER`, `MONGO_PASSWORD`), separate from Postgres (`DB_USER`, `DB_PASSWORD`); it is created only on the first start of an empty volume, so changing it later needs a new `mongo_data` volume (the read model is rebuilt from Postgres on the next start). `init.sql` creates the `keycloak` and `receipt-analyzer-service` databases on the first start of the postgres container. `dev/realm-export.json` is the Keycloak realm (`activiti`, client `web-client`), imported on first start; it contains no users, so a fresh Keycloak needs a user created in the admin console. `dev/resetdb.sql` drops the app tables.

Backend env vars required by `adapters/src/main/resources/application.yml`: `DB_URL`, `DB_USER`, `DB_PASSWORD`, `MONGODB_URI`, `KAFKA_BOOTSTRAP_SERVERS`, `KEYCLOAK_ISSUER_URI`, `KEYCLOAK_JWK_SET_URI`, `WEB_CLIENT_HOST`. The schema is versioned with Flyway: migrations live in `adapters/src/main/resources/db/migration` (`V<n>__<description>.sql`) and run on startup. Hibernate runs with `ddl-auto: validate`, so every entity change needs a new migration (never edit an applied one) or the app fails to start. The users table is `app_user` (`user` is reserved in PostgreSQL), and text comparisons in queries are case-sensitive in PostgreSQL, so searches use `LOWER(...)`. The OCR data path defaults to `/app/tesseract-data` (container path); outside Docker, point `ocr.tesseract.dataPath` at `receipt-analyzer-service/tesseract-data`.

## Request routing

The browser talks only to Nginx (`nginx.conf`): `/auth/` goes to Keycloak and `/api/` to the backend. The backend uses servlet context path `/api`, so controller mappings like `/wallets` are served at `/api/wallets`. In dev, `ng serve` proxies `/api/**` to `http://localhost/` (Nginx) through `proxy.conf.json`. The backend is a stateless OAuth2 resource server: every endpoint except `/actuator/health/**` requires a Keycloak JWT, and controllers identify the user by `jwt.getSubject()`.

## Backend architecture (hexagonal + CQRS)

Gradle modules and their dependency direction:
- `domain`: domain entities (`Receipt`, `ReceiptRevision`, `Wallet`, `ProductDict`, …) and **write-side** repository ports (`WalletRepository`, …). Depends only on Lombok and framework-free libraries (e.g. `commons-text` for Levenshtein in `ProductMatcher`), never on Spring or JPA. Entities and ports are mostly package-private.
- `app`: use cases. Each feature exposes a `*Facade`, plus **read-side** ports (`*QueryRepository`), factories and DTOs/requests/responses under `model/`. No Spring annotations: facades are plain classes.
- `adapters`: Spring web/JPA/security. REST controllers, JPA entities (`Sql*`), repository implementations, and the `*Configuration` classes that wire facades as `@Bean`s by hand.
- `monolith`: only `ReceiptAnalyzerServiceApplication` (the Spring Boot entry point), which depends on `adapters`.

Conventions that span modules:
- **Split packages by feature.** The same package (e.g. `pl.madzierski.daniel.wallet`) exists in `domain`, `app` and `adapters`. Facade methods, domain classes and ports are package-private, so a controller must live in the same feature package as the facade it calls. Keep new code inside the matching feature package in each module.
- **Write side:** a domain port such as `WalletRepository` is implemented in adapters by a package-private `*RepositoryImpl` that wraps a Spring Data `Sql*Repository` and maps through `SqlX.fromX(...)` / `toX()`.
- **Read side:** every GET is served from MongoDB, never from Postgres (see Read model below). It mirrors the write side: a document `MongoX` (`@Document` record with `fromEvent(...)` and `toDto()`, indexes as `@Indexed`) and a Spring Data `MongoXRepository` in `MongoXRepository.java`, next to the `XQueryRepositoryImpl` that implements the app port (e.g. `WalletQueryRepository`). These and the `XProjector` live in the feature's `readmodel` subpackage (e.g. `receipt/readmodel`), which Spring Modulith keeps internal to the module; `XEventMapper` and `XSnapshotSource` stay in the feature package, because the write repositories use them. Use derived queries, `@Query`, `@Update` and `@Collation`; `MongoTemplate` only in a repository fragment for what annotations cannot express (`ItemProductReassignment`). Repositories (JPA and Mongo) query only their own feature's tables and collections. Reads that a command needs for its own checks (ownership, existence, usage) are write-side ports on Postgres, e.g. `ReceiptRepository.findAccessible`, `ReceiptRevisionRepository.hasChildRevisions`; a check on another feature's data goes through that feature, either a public facade method (`WalletFacade.isWalletAccessible`, `StoreFacade.storeExists`) or, when that feature depends on the caller, a port the other feature implements (`ReceiptLookup`, below). The only Postgres query port left is `UserQueryRepository`, because every request resolves its user through it.
- `Sql*Query` entities are lightweight reference mappings to roots of the same feature; an entity refers to another feature's aggregate only by a plain `UUID` column (`SqlReceipt.walletId`/`storeId`, `SqlReceiptItem.productId`, `SqlReceiptRevision.sourceFileGroupId`, `SqlWallet.ownerId`, `SqlFileGroup.receiptId`), so no entity maps another feature's table (the foreign keys stay in the database). `*Query` domain models (e.g. `UserQuery`, `FileGroupQuery`) are id references to other aggregates.
- Every JPA entity extends `common.entity.BaseEntity` (adapters), which holds `id` (`@UuidGenerator`), `createdDate` and `modifiedDate` (Spring Data auditing). Subclasses use `@EqualsAndHashCode(callSuper = true)` so the id stays part of equality, and set the inherited fields with setters, since Lombok constructors and builders only cover a class's own fields. Aggregate roots (`SqlReceipt`, `SqlReceiptRevision`, `SqlWallet`, `SqlStore`, `SqlStoreBrand`, `SqlProductDict`, `SqlProductCategory`, `SqlFileGroup`) extend `VersionedEntity` instead, which adds the `@Version` column `version` (V11); child entities (items, aliases, files) are not versioned, and a change of children raises the root's version because the root's collection is replaced on save. A root's references to other roots use the unversioned `Sql*Query` mappings (e.g. `SqlReceiptQuery`, `SqlReceiptRevisionQuery`), because a versioned stub with only an id and no version counts as a new entity in Hibernate.
- **State changes go through aggregates:** load the aggregate (e.g. `findByIdWithItems`), call a domain method, save it. Read-side queries may decide which aggregate to load, but never modify data. Bulk JPQL updates are only for mass operations across many aggregates that break no domain rule (e.g. `reassignProductDict` when merging products), and they must publish an event of their own (`ItemProductsReassigned`), because the read model only learns about changes through events.
- **Optimistic locking:** domain aggregates carry `version` (from `SqlX.toX()`, back through `SqlX.fromX(...)`), read DTOs and responses return it, and edit requests send it back (`UpdateReceiptRequest`, `UpdateRevisionRequest`, `UpdateProductCategoryRequest`, `UpdateProductDictListRequest.UpdateProductDict` for the primary product, all `@NotNull`). The facade compares it with the loaded aggregate before changing it and throws `VERSION_CONFLICT` (409), so an edit made from stale data never overwrites a newer one; a race between two transactions ends in Hibernate's optimistic lock exception, which `GlobalExceptionController` maps to the same 409. Actions on the current state (copy, learn aliases, rewrite names, delete) send no version. The web client keeps the version from the GET, sends it with the edit and reloads the data on 409 (`error/version-conflict.ts`).
- **Commands return ids, queries return data.** Facade methods that change state (create, update, copy) return a response with only the id (e.g. `CreateReceiptResponse(id)`, `UpdateRevisionResponse(id)`); the client fetches fresh data through a query endpoint. The response also carries `X-Consistency-Token` (see Read model). Response records build themselves from read-side DTOs through constructors, and each response keeps its own nested records.
- **Factory vs mapper (app):** a `*Factory` creates a new domain object that will get its own identity and be saved (`ReceiptFactory.from(request, user)` calls `Receipt.create`), and may combine several inputs or hold creation logic. A `*Mapper` (static methods, next to the facade in the feature package) only reshapes data one to one without logic, e.g. a request into a domain value object (`ReceiptMapper.toItemChange` builds a `ReceiptItemChange`); the aggregate decides what the data means. JPA mapping stays in `SqlX.fromX(...)` / `toX()`.
- Errors: throw `AppRuntimeException` with a constant from `AppRuntimeExceptionMessages`. `GlobalExceptionController` turns it into the HTTP response. Domain classes cannot see it (it lives in `app` and uses Spring's `HttpStatus`), so a broken domain rule that the facade should have prevented throws `AppIllegalStateException` with a constant from `AppIllegalStateExceptionMessages` (domain, codes only); it is logged as an error and returned as 500 Internal Server Error, because reaching it means a bug, and 409 is kept for version conflicts only.
- **Ownership (IDOR):** controllers take an `AuthenticatedUser user` parameter (app record holding `app_user.id`, resolved from the JWT `sub` by `security.AuthenticatedUserArgumentResolver` with a Caffeine cache) and pass it to the facade, which maps it to the domain `UserQuery` with `toUserQuery()` for ports and owner fields. Naming: in requests (controllers, facades, ports) it is `user`, because it is only the requester until the query proves ownership; in domain models and JPA entities the field is `owner` (`Receipt`/`FileGroup`: column `owner_id`, `Wallet`: column `user_id`). Ownership is part of the query (`findAccessible(id, user)`, `... AND r.ownerId = :ownerId`), never a separate check, and someone else's resource throws the same `*_NOT_FOUND` as a missing one. Children (revisions, items, files) are checked through their root.
- Facades never depend on each other in a circle, and `@Lazy` is not used to hide one. When a feature must trigger work in a feature that already depends on it, it declares a public port in its own `app` package and the other feature implements it: `product_dict` defines `MergedProductReassignment`, which `receipt` implements in `ReceiptMergedProductReassignment` (on `ReceiptRevisionRepository`, not `ReceiptFacade`, so there is no bean cycle either) and wires in `ReceiptConfiguration`; likewise `file_group` defines `ReceiptLookup` (is the receipt accessible, is a file group the source of a revision), implemented by `ReceiptLookupImpl`.
- Spring Modulith treats each feature package as a module whose subpackages are internal. `ApplicationModulesUT` checks the module rules, and a dependency goes one way only (a cycle fails it): e.g. the receipts of a wallet are served by `receipt` (`GET /receipts?walletId=…` in `ReceiptController`), so `wallet` knows nothing about receipts, and `FileGroup` keeps a plain `receiptId`. A subpackage that other features use (`model`) is exposed with `@NamedInterface` in a `package-info.java` kept in `adapters`, so `app` and `domain` stay free of Spring; `common` is an open module.

Features: `receipt`, `digitization` (reading data from receipt files, see below), `wallet`, `file_group` (uploaded files grouped per receipt, type detection via Tika; all parts of a group share one type, checked by `FileGroup`; `LocalFilePathPolicy` gives each file a path relative to `file.upload-dir` (`user/<owner>/receipts/<receipt>/file_group/<group>/file/<file>.<ext>`), which `LocalFileStorage` resolves against that directory, while older absolute paths are used as they are), `product_dict` (product dictionary, aliases and categories; aliases belong to the `ProductDict` aggregate and have no repository of their own, so renaming and merging go through `ProductDict.rename(name, keptAliasIds, mergedProducts)`, which copies the chosen aliases of merged products as new aliases; alias matching lives in the domain `ProductMatcher`, fuzzy matching threshold `product-dict.min-required-similarity`), `store`, `user`.

### Read model (CQRS with outbox, Kafka and MongoDB)

Postgres is the write model and the source of truth; MongoDB holds a read model derived from it and can always be rebuilt.
1. **Events:** every write repository adapter (`*RepositoryImpl`) registers an integration event on `save` or delete: a snapshot of the whole aggregate through `EventPublisher.publishLatest(id, () -> snapshot)`, built only before commit from the final state, so an aggregate saved several times in one transaction yields one event (`WalletChanged`, `ReceiptChanged`, `RevisionChanged`, …) or a deletion (`ReceiptDeleted`, …). Event records live in `app/<feature>/event` and implement `IntegrationEvent`; snapshots are built by the static `changed(...)` methods of the feature's `XEventMapper` class, which the repository and the feature's `XSnapshotSource` (the rebuild) share. `event.EventTypes` finds event types by scanning the classpath for `IntegrationEvent` implementations and keys them by simple class name (the `type` of the envelope), so that name must be unique.
2. **Outbox (Spring Modulith):** `PendingEvents` keeps the events of the transaction; in `beforeCommit` `OutboxEventPublisher` flushes the aggregates (so snapshots carry the audit dates and the version of the committed row) and publishes a `PublishedEvent` envelope (event id, correlation id, aggregate id, type, JSON payload) through `ApplicationEventPublisher`. Spring Modulith stores it in its event publication registry (table `event_publication`, V10, `spring-modulith-starter-jdbc`) in the same transaction. Tests never commit, so `IntegrationTest.publishPendingEvents()` (called by `flush()`, `outboxEvents()` and `projectOutboxEvents()`) does that step by hand. All events of one transaction share a `correlation_id` (`TransactionCorrelation`, bound to the transaction). Facades never publish themselves; a change that bypasses an aggregate (bulk JPQL, DB cascade) needs its own event, or the facade must change the aggregate explicitly (e.g. `deleteRevision` unmarks the preferred revision on the `Receipt` instead of relying on `ON DELETE SET NULL`).
3. **Externalization:** after commit Modulith sends the envelope asynchronously to the single-partition topic `receipt-analyzer.events` (`@Externalized` on `PublishedEvent`, key = aggregate id, value = the envelope as JSON, configured in `KafkaEventConfiguration`; `spring.modulith.events.kafka.enable-json: false` keeps the String serializer) and deletes the publication once Kafka confirms (`completion-mode: delete`). A failed publication stays in the registry and `EventResubmissionSchedule` (`read-model.resubmission.enabled`) resubmits publications older than 30 s every minute. Delivery is at least once and not ordered.
4. **Projections:** `ReadModelEventListener` (`read-model.listener.enabled`) hands each event to `ReadModelProjector`, which passes it to every feature's `XProjector` (`readmodel.Projector`) and skips event ids already in `processed_events` (TTL 7 days) and snapshots (`AggregateChanged`) whose `version` is not newer than the last one projected for that aggregate (`projected_versions`); a deletion (`AggregateDeleted`) leaves a tombstone there, so a late snapshot cannot bring a deleted document back. Optimistic locking makes versions of one aggregate grow in commit order, so no global sequence is needed. `ItemProductsReassigned` is an operation, not aggregate state (plain `IntegrationEvent`), so it bypasses that check. Projections only upsert or delete documents of their own aggregate (`wallets`, `stores`, `store_brands`, `product_dicts`, `product_categories`, `file_groups`, `receipts`, `revisions`), except names of referenced aggregates that a list shows: `stores` keep the brand name and `product_dicts` the category names, taken from `store_brands` / `product_categories` when the store or product is projected and rewritten in all documents when the brand or category is renamed; otherwise the query adapters join only their own collections at read time (`isPreferredRevision` from `receipts.preferredRevisionId`, the preferred revision of each wallet receipt), and data of another feature comes through that feature's query port: `ReceiptFacade` takes stores from `StoreQueryRepository`, and `ReceiptItemQueryRepositoryImpl` takes item names of non-`USER` revisions from `ProductDictQueryRepository.findNamesByIds`, so renaming a product touches one document.
5. **Read your writes:** `ConsistencyTokenFilter` adds `X-Consistency-Token: <correlationId>:<event count>` to command responses whose transaction published events. A GET that sends the token back waits in `ReadModelConsistencyInterceptor` until all those events are processed (`read-model.consistency-timeout`, default 3 s), otherwise it answers with `X-Read-Model-Stale: true`. The web client does this in `consistency/consistency-token.interceptor.ts`: it keeps the last token and sends it with the next GETs.
6. **Rebuild:** `ReadModelRebuild` publishes snapshots of all aggregates (`ReadModelSnapshotSource`, ordered so brands come before stores) through the outbox: on the first start against an empty Mongo (`projection_meta` missing, `read-model.rebuild-on-start`) or on every start with `read-model.force-rebuild=true` (env `READ_MODEL_FORCE_REBUILD`), e.g. after changing a projection.

### Receipts, revisions and resolvers

A `Receipt` has many `ReceiptRevision`s, forming a tree through `parentReceiptRevision`. Each revision records the `resolver` (a `ReceiptResolverStrategyType`) that produced it, plus an `isCorrect` flag. The preferred revision belongs to the `Receipt` (`preferred_revision_id`, set with `Receipt.choosePreferredRevision`), so a receipt has at most one by design. Machine-produced revisions come from resolvers. User edits create user revisions (`UserResolver`), and only those are meant to be editable in the UI. Updating a revision (`PUT /revisions/{id}`) replaces its summary with the sent values, so the client sends the whole revision: a missing `totalPrice` or `paymentDate` clears it and a missing `isCorrect` means `false`. A revision whose items add up to its total is always marked correct (`markCorrect` cannot unmark it). File parts of a group are numbered by `partNumber`; `FileFacade.getFiles` returns them in that order for digitization, while receipt details return them unordered.

Reading data from receipt files is a separate `digitization` feature (`app/.../digitization`, wired in `adapters/.../digitization/DigitizationConfiguration`). `ReceiptFacade` only calls `DigitizationFacade.digitize(files, strategy)`, which returns a `DigitizedReceipt`, and builds the revision from it, so the receipt feature knows no parser. Digitization uses the strategy pattern: `ReceiptResolverStrategy` implementations (`BiedronkaScanResolver` for PDF→OCR, `BiedronkaJsonResolver`, `UserResolver`, in `digitization/impl`) are beans, and `DigitizationFacade` picks one by `strategy()`. `ReceiptResolverStrategyType` lives in the `digitization` package of the `domain` module, because revisions persist it and `receipt` depends on `digitization`, not the other way round. To support a new store or format:
1. add an enum value to `ReceiptResolverStrategyType`;
2. implement the strategy in `digitization/impl`;
3. register it as a bean in `DigitizationConfiguration`;
4. optionally add a `receipt-resolver-strategy.<name>.version` property.

## Frontend structure

`src/app` has a flat layout. Route-level pages are top-level folders (`wallet-list`, `receipt-details`, …), reusable pieces live in `component/`, HTTP services in `service/` and interfaces in `model/`. The HTTP interceptors have their own folders: `consistency/` (sends back the last `X-Consistency-Token`) and `error/` (error dialog, reload on a 409 version conflict). `keycloak-angular`'s bearer interceptor attaches the token to every request (`app.config.ts`). The app is served under the `/home/` base path. Environment files hold `keycloakUrl` / `apiUrl`.

## Deployment

`dockhand/` contains the production compose file, nginx config, realm export and a `Jenkinsfile`. Jenkins first runs all tests with `gradle test`, i.e. domain unit tests and integration tests (`Test` stage, `gradle:9.3.0-jdk21` image with the Docker socket mounted for Testcontainers; a failing test stops the pipeline), then builds the backend and web client images and pushes them to a private registry as `receipt-analyzer-service` and `receipt-analyzer-web-client`, each tagged `0.0.<build>` and `:latest`, and finally calls the Dockhand webhook, which redeploys the stack. The production compose also runs MongoDB and Kafka on the internal network only, with external volumes `receipt_analyzer_mongo_data` and `receipt_analyzer_kafka_data` (create them before the first deploy, like the Postgres one). Its `.env` needs `MONGO_USER` and `MONGO_PASSWORD` (letters and digits only, they go into `MONGODB_URI`). The backend Dockerfile builds `:monolith:bootJar -x test` and installs `tesseract-ocr` in the runtime image.

## Commits

Branches are named after Jira-style tickets (e.g. `maintenance-3-rec-38`). Commit messages are short, lowercase and end with `closes REC-<n>`.
